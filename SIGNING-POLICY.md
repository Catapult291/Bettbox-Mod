# Code Signing Policy

This document defines the code signing policy for the **Bettbox-Mod** project (a fork of
[appshubcc/Bettbox](https://github.com/appshubcc/Bettbox)), utilizing the free open-source
code signing service provided by the [SignPath Foundation](https://signpath.org/).

## 1. Scope

This policy applies to all Windows executable artifacts distributed by this project:

- `Bettbox.exe` — the main application executable
- `BettboxCore.exe` — the clash core process
- `BettboxHelperService.exe` — the helper service executable
- `bettbox_native.dll` — the Rust native library (config pipeline + script engine)
- `WindowsLoopbackManager.exe` — the UWP loopback exemption tool
- The Windows installer (`Bettbox-*-windows-*-setup.exe` generated by Inno Setup)

Third-party/runtime binaries bundled by Flutter or plugins are distributed as-is and are
outside this policy's scope.

## 2. Roles and Responsibilities

- **Project Maintainers**: Only authorized maintainers can push to the default branch
  (`main`), create release tags, and manage repository settings/secrets.
- **SignPath Service**: Provides the code signing certificate and handles the cryptographic
  signing process securely in the cloud.

## 3. Security and Branch Protection

To ensure that only trusted and reviewed code gets signed, the project should enforce:

- **Protected Branches**: The `main` branch is protected.
- **Code Review**: Changes must land via Pull Requests (direct pushes restricted).
- **Two-Factor Authentication (2FA)**: All maintainers with write access should enable 2FA.

## 4. Build and Signing Process

Signing is fully automated; manual code signing for official releases is not permitted.

- **CI/CD Automation**: All signing operations run in GitHub Actions
  (`.github/workflows/build.yaml`).
- **Trigger Conditions**: Signing only runs when **both** hold:
  1. `SIGNPATH_API_TOKEN` is configured as a repository secret;
  2. the run is on a version tag (`refs/tags/v*`) — plain branch/`workflow_dispatch`
     builds stay unsigned.
- **Ephemeral Environments**: Builds compile on isolated GitHub-hosted runners; artifacts
  are uploaded to SignPath, signed in the cloud, and downloaded back in place.
- **Signing Policies** (slug names must exist in the SignPath project and match the
  workflow):
  - `release-signing` — stable tags (`v*` without `-`), and the installer on prerelease tags.
  - `test-signing` — executables on prerelease tags and non-stable edge cases.
- **Ordering Invariants** (encoded in the workflow, do not reorder casually):
  - Core is signed **before** the helper build — the helper embeds the SHA256 of the signed
    core as its TOKEN, and the app computes `CORE_SHA256` from the same signed file.
  - `bettbox_native.dll` / `WindowsLoopbackManager.exe` are signed **after** the
    bundle-hash verification and Dart tests — signing rewrites the file and would otherwise
    break the "bundle copy == cargo artifact" assertion.
  - The installer is signed **after** Inno Setup packaging (the inner files are already
    signed when compressed into it).
- **Distribution**: Signed artifacts are uploaded as `Bettbox-*` and published to the
  GitHub Releases page; intermediate unsigned artifacts are deleted at the end of the run.

## 5. Required Repository Configuration

| Where | Name | Content |
|-------|------|---------|
| Secret | `SIGNPATH_API_TOKEN` | SignPath API token (signing is skipped entirely while absent) |
| Variable | `SIGNPATH_ORG_ID` | SignPath organization UUID of this fork's own organization |
| Variable | `SIGNPATH_PROJECT_SLUG` | SignPath project slug (e.g. `bettbox-mod`) |

This fork **cannot** reuse the upstream project's SignPath organization, project, or token —
each has its own SignPath OSS registration.

## 6. Incident Response and Revocation

If a security breach, unauthorized commit, or CI token compromise is suspected:

1. Maintainers immediately revoke any exposed tokens.
2. If malicious code was signed, maintainers immediately contact SignPath Foundation to
   request revocation of the code signing certificate.
3. An advisory is published on the repository to notify users.
